# Decisions log

Every business rule and open question we settle, in order. Per the ground rules (Section 15): thresholds not specified in the build prompt get asked, not invented.

## M0 — deployable skeleton

- **Backend:** Node 20 + TypeScript + Fastify. The build prompt (Section 12) allowed either Node+TS or Python+FastAPI and said to just pick one — picked Node so the backend, web console, and mobile app (Expo/React Native) can eventually share TypeScript types, which matters for one person maintaining this.
- **Mobile:** React Native (Expo) — not scaffolded yet. Per Section 13, M0 is infra only; the app starts at M2.
- **Web console:** plain React (Vite) — not scaffolded yet. Per Section 13's build-order note, the web POS shell arrives by M4; full parity is M13.
- **Database:** PostgreSQL 16, run in Docker alongside the API for now (Section 12 calls Postgres non-negotiable; managed vs self-hosted is an infra choice you can change later without touching the app).
- **Migrations:** node-pg-migrate — plain, reversible SQL/JS migration files, run as an explicit deploy step (`deploy.sh`), never automatically on boot (Section 12B.2, Section 15).
- **Monorepo:** npm workspaces (`apps/*`, `packages/*`). No extra tooling (pnpm/turborepo) — kept to what ships with Node, per "optimise for one person maintaining it."
- **Reverse proxy / TLS:** Caddy, automatic Let's Encrypt renewal, per Section 12B.1.
- **Theme tokens created in M0** (`packages/theme`) per Section 12C.5. This environment can't reach `dipashamedicalstore.in` directly, so the values weren't pulled from the live CSS — they were read visually off the logo and a homepage screenshot the owner provided instead: `brandGreen #167A4B`, `brandGreenDark #0F5C39`, `brandGreenTint #EAF7F1`, near-black heading text, grey body text. Close estimates, not pixel-sampled. **Open item: swap in exact hex codes from the site's stylesheet if pixel-perfect matching ever matters** (see `packages/theme/README.md`).
- **Logo carries a third colour** (orange-red, on the ring and one pill capsule in the mark) that Section 12C's "white and green" framing didn't anticipate. Site chrome itself — buttons, headings, backgrounds — is white/green throughout with no orange visible, so it's excluded from the token set for now. Not used anywhere unless asked for later (e.g. a WhatsApp-styled accent).

## M1 — data model, migrations, auth, role framework

- **MRP and cost live on the batch, not the SKU.** Section 5's product-field list mentions `mrp`, `purchase_price`, `margin` on the product, but Section 9A.8 and Section 6.5 are explicit and detailed that MRP varies by batch and effective cost is computed per batch from the actual purchase line — "getting this wrong causes customer disputes." Followed the later, more specific sections; `products` carries no cost/price columns, `batches` carries `mrp` and `effective_cost_per_base_unit`. Margin is always derived, never stored flat.
- **`stock` is a SQL VIEW, not a table** — `SUM(quantity_delta)` grouped by `(product_id, bin_id, batch_id)`, computed from `movement_ledger`. This makes the ground rule ("if you find yourself writing an UPDATE against a quantity column, stop") impossible to violate by accident: there's no quantity column to update anywhere.
- **`movement_ledger` immutability is a database trigger**, not just an application convention — `UPDATE`/`DELETE` raise a Postgres exception. Verified this actually blocks a raw `UPDATE` in testing, not just app-layer writes.
- **`transfer` and multi-batch sale lines write multiple single-effect ledger rows** sharing a `transfer_group_id`, rather than one row with two bin columns — keeps every row an unambiguous single stock effect, consistent with how Section 6A.2 describes a multi-batch sale auto-splitting into sub-lines.
- **Seeded opening-stock batches are marked `cost_unknown = true`.** Section 6.5 names this exact scenario — "opening stock entered at go-live without purchase history" — as the case for `cost_unknown` rather than a fabricated cost or zero. The seed script's 50 dummy SKUs have no real purchase invoice behind them, so this is the documented-correct choice, not a shortcut.
- **OTP delivery is a pluggable interface** (`OtpSender`) with a dev console sender that logs the code and echoes it in the API response **only when `NODE_ENV=development`**. No real SMS/WhatsApp provider exists yet (Section 14 — the owner's account to set up; wired properly in M8). The API refuses to boot in production without `JWT_SECRET` set, so this can't silently ship half-configured.
- **Owner impersonation (Section 3)** issues a new access token with the impersonated role, but `sub` (the actor id) always stays the real owner's id — every audit stamp downstream traces back to who was actually logged in, never the impersonated identity. Impersonated sessions can't mint their own refresh tokens, so a leaked impersonated access token expires with the access-token TTL and can't be silently renewed.
- **PIN re-entry (Section 3 idle-lock)** requires both a still-valid refresh token *and* the PIN — never the PIN alone — so a shoulder-surfed 4-digit code can't unlock a session without also holding the device's stored session.
- Settings seeded in M1 are only the ones with a stated default already in scope for M1's own logic or explicitly given as a global default elsewhere in the doc (session lock timing, cycle count size, near-expiry pick block, etc.) — thresholds tied to a feature not yet built (e.g. write-off approval value) get added in that feature's own migration instead of guessed now.

## M2 — product master, bin master, label printing, unified search

- **Web console scaffolded now** (`apps/web`, plain React + Vite, per the M0 decision) — first real UI, per Section 13's note that the web POS shell needs to exist well before M13. No router library yet (simple state-based tab switching); will add one once the console has enough screens to need it (M4+).
- **Product creation duplicate detection is a 409, not a hard block** — matches Section 6A.9's general "no hard blocks" philosophy even though Section 6B.2 doesn't use that exact phrase for this case. The client shows the existing matches and can resubmit with `confirmDuplicate: true` to proceed anyway, or link a substitute instead.
- **Auth tokens stored in `localStorage`** on the web console — pragmatic for an internal staff tool behind its own auth flow. Worth revisiting (httpOnly cookies + CSRF) if this console is ever exposed more broadly before the real deployment; flagged in `apps/web/src/api.ts`.
- **Unified search ranking**: Postgres trigram similarity (`pg_trgm`) across product name/manufacturer and salt name/synonym, with a hand-tuned score threshold to decide brand-search vs salt-search mode. **Known limitation**: Section 5B.3's "multi-salt search: typing two salts matches combination products containing both" isn't implemented yet — current matching is single-term. Revisit if a real combination-drug search need shows up before then; not blocking M2's stated scope.
- **Search's "brand exact match" pulls in the rest of its substitute group explicitly** — trigram matching alone won't find sibling brands that don't share text with the query (searching "dolo" doesn't lexically match "paracetamol"), so the search does a second lookup by `substitute_group_id` once a strong brand match is found. Caught this in testing before it shipped: the group-expansion header ("Paracetamol 650mg — 6 other brands in stock") was empty without it.
- **Internal barcodes** (Section 9A.5) use a "290" GS1 restricted-circulation-number prefix, so they can never collide with a real manufacturer barcode added later.
- **Bin label sheet**: A4, 3×8 grid, QR encodes the bin code (not an internal ID) so a scan resolves to something a human can also read off the printed label. Black and white only, per Section 12C.3 — no brand colour on anything meant for a thermal or laser printer.

## M3 — GST purchase entry, stock_received, put-away

- **Purchase entry API works in base units throughout, not per-pack.** Real distributor invoices state quantity and rate per strip/box, but every quantity in this system (ledger, stock, batches) is base units (Section 5A.1). Rather than have the API guess a conversion, the web UI's dual-entry `QuantityInput` component converts strips-and-loose to base units — and "rate per pack" to "rate per base unit" — before the request goes out, the same way Section 5A.2 describes for billing. The API itself only ever sees base units and a per-base-unit rate.
- **GST is computed on line-level taxable value only.** Bill-level discount and freight/charges (Section 6.4/6.5) adjust landed cost and net payable, but are *not* treated as reducing the GST taxable value per line. This is a real, debatable GST-technical judgment call, not a certainty — **flagged for the owner's accountant to confirm** before this is relied on for actual filing (see `apps/api/src/domain/gst-split.ts`).
- **`shop_gst_state_code` seeded as "09" (Uttar Pradesh)**, inferred from the Prayagraj address in the brief, not from an actual GSTIN nobody's given me yet. **Needs confirming against the shop's real GSTIN before this goes near a real invoice.**
- **Duplicate `(vendor, invoice_number)` is a true hard block** (409, no override) — Section 6.2 states this flatly with no override language, unlike the near-expiry and reconciliation-mismatch checks next to it, which are soft (warn, require an explicit override/acknowledge flag to proceed).
- **Cold-chain → CC-\* and Schedule H1 → SH-\* put-away zone forcing is a genuine hard block** (Section 6.6, point 4) — the one deliberate exception to this build's general "no hard blocks" posture, because it's a physical/regulatory placement constraint, not a pricing or workflow judgment call. Verified live: confirming a cold-chain item into a regular bin is rejected; the same bin works fine for a non-restricted product.
- **Every put-away confirmation right now is `source: web_manual`, unconditionally.** Section 10.1 reserves manual bin entry (with a mandatory reason code) for the web console specifically, because it has no scanner — but since the Android app doesn't exist yet (still an open item, see below), *every* put-away in this build today goes through that same no-scanner path. Once a real scanning client exists, it gets its own `source: app` path with a genuine QR scan and no reason-code requirement.
- **Same-batch re-receipt doesn't blend cost.** If a GST purchase or stock-received line reuses a `(product, batch_no)` that already exists, the existing batch row (and its already-established effective cost) is reused as-is; the new receipt just adds a further ledger row. The brief doesn't specify a cost-blending rule for a genuinely repeated batch number, so this wasn't invented — see `apps/api/src/repo/batches.ts`.
- **No separate "received vs. invoiced" variance step in M3.** Section 6.6 mentions "invoice-versus-received variance is logged" but this build takes what's entered on the purchase line as what was received — there's no separate physical-count-at-receipt step distinct from data entry yet. That distinct receiving-count workflow doesn't have a clear home until cycle counts (M6); flagging rather than quietly building a mismatched version of it now.
- **Purchase entry restricted to Owner and Store Manager** (Section 3's table lists "Inbound/GRN" under Store Manager); put-away confirmation is open to Owner, Store Manager, and Picker/Packer, since Section 6.6 explicitly describes "the picker" doing the scan.

## M4 — counter POS and GST billing, stock_issue, sale returns, day-close

- **Scope deliberately trimmed, and stated here rather than silently dropped.** Offline mode is explicitly M12 by the doc's own build order ("late by design"). WhatsApp bill notification is M8. Full customer credit ledger/ageing/statements are M9A/M15 — a `credit` tender type is recorded and an outstanding amount exists on the bill, but there's no ledger, limit warning, or statement yet. Delivery's own pick/pack/dispatch lifecycle is M7/M10 — the `sales.channel` field exists so the schema doesn't need to change later, but only the counter path is wired end to end.
- **Hold/recall and draft/quotation are a plain JSONB parking table (`held_bills`), not half-formed `sales` rows.** A `sales` row only ever represents a real, completed transaction — FEFO-committed batches, stock deducted, a real gapless bill number — as final as a ledger entry. This avoids nullable-batch/bin columns on `sale_lines` that would only exist to support an in-progress state, and keeps "a sale exists" mean the same thing everywhere else it's read (reports, the H/H1 register, day-close).
- **Bill and credit-note numbering is gapless by construction, not by convention.** The counter increments inside the same transaction as the row it numbers (`apps/api/src/domain/bill-numbering.ts`), so a rolled-back sale rolls back the number it reserved too — unlike a Postgres `SEQUENCE`, which never rolls back and would leave exactly the audit gap Section 6A.6 warns about. Verified: `DPS-000001`, `DPS-000002`, `DPS-000003`... with no gaps across every test sale, including ones that never actually completed.
- **Counter sales are always intra-state (CGST+SGST 50/50), no IGST case.** Unlike purchases, where the vendor could genuinely be out-of-state, a counter sale's customer is physically in the shop — there's no out-of-state counter transaction to split for. `apps/api/src/repo/sales.ts`'s `splitCounterGst` is deliberately simpler than the purchase-side `gst-split.ts`, not an oversight.
- **"Selling below available stock is blocked; negative stock is never permitted" (Section 6A.2) is enforced by construction, not a separate check** — FEFO allocation itself throws if total available stock is less than requested, before any ledger row is written. Verified live: a 1000-unit request against 155 in stock was rejected with the real available/requested numbers, no partial sale created.
- **Minimum-margin discount floor not implemented — only the zero-margin floor is.** Section 6A.9 asks for "the maximum discount... to zero margin, and separately to a configurable minimum-margin threshold," but gives no default for that threshold, and Section 15's ground rule is to ask rather than invent one. The POS shows the zero-margin floor (computed, unambiguous) live per line; the minimum-margin floor is a follow-up once a real threshold number exists.
- **Receipt printing is a browser-printable HTML view, not ESC/POS thermal output or an A4 GST invoice PDF yet.** This sandbox has no real thermal printer to develop against, and PDF invoice generation is a reasonable near-term addition (the `pdf-lib` pattern already exists from bin labels) rather than something to rush now. The current receipt already carries every statutory field Section 6A.6 asks for — bill number/date, per-line batch/expiry/HSN, GST breakdown — except the shop's real GSTIN and drug licence numbers, which show as `[pending]` until the owner provides them.
- **Billing is gated to Owner and Store Manager**, same reasoning as purchase entry: Section 3's role table has no distinct "biller" role, and Picker/Packer is explicitly read-only stock lookup. **Worth confirming directly** — a real pharmacy counter is usually staffed by someone other than the manager personally, and this table may need a fifth role the brief doesn't currently name.
- **Two real bugs found and fixed during end-to-end verification, not left for later**: an ambiguous ordering mistake in the "brand exact match" query would've silently omitted sibling products in some cases (see M2 note, still applicable pattern here); and this milestone specifically, a wrong column reference (`batches.hsn_code` instead of `products.hsn_code`) in the bill-detail query, and a client-side bug where the API helper sent a JSON content-type header on bodyless POSTs, which Fastify rejects outright. Both caught by actually printing a receipt through the real UI, not just by reading the code.

## M5 — customer request book, purchase orders, callback loop, daily review

- **`sellable_stock` is a new view layered on top of `stock`, not a change to `stock` itself.** `stock` still means "what's physically on the shelf" (Section 6B.4's own framing: reserved stock is *excluded from sellable quantity*, not physically moved). FEFO allocation, search's stock display, and the reorder/PO suggestion logic were all repointed at `sellable_stock`; the movement ledger and `stock` view are untouched, so a reservation never writes a ledger row of its own — only its later release or fulfilment does, indirectly, via the sale it enables.
- **Real bug caught and fixed during end-to-end verification, not left as a known issue**: a failed sale (e.g. insufficient tender) was permanently releasing the customer's stock reservation, because the release UPDATE ran on the plain connection pool *before* the sale's own transaction opened — so when the sale rolled back, the release didn't roll back with it. Fixed by moving `BEGIN` to the very first statement in `createSale` and threading that same transactional client through the reservation release, the FEFO allocation, and every insert (`apps/api/src/domain/fefo.ts`, `apps/api/src/repo/sales.ts`). Confirmed with a real failed-then-successful fulfilment pair against Postgres, not just by reading the diff.
- **PO suggestions only auto-add a requested item if current sellable stock is already below what's been asked for** (Section 6B.3's own rule, quoted almost verbatim) — if stock arrived in the meantime, the request simply drops off the suggested-lines screen rather than double-ordering; it's still sitting there as an `open` request waiting for the callback loop (GRN → `checkCallbackMatches`) to pick it up on its own.
- **A PO ships to exactly one vendor.** `createPurchaseOrder` takes a single `vendorId` for the whole order — the suggested-lines screen shows a per-line "last vendor purchased from" as a hint, but doesn't split one PO across vendors automatically. Placing orders with two different vendors from one review pass means running the screen twice, once per vendor.
- **`PATCH /requests/:id/unreachable` added in this milestone's web-UI pass**, wiring a repo function (`incrementUnreachableAttempts`) that existed since the schema/CRUD pass but had no route — the callback queue's "could not reach customer" action needed it and there was no reason to leave a written-but-unreachable function sitting idle.
- **The callback queue and the "Daily Request Review" screen are two different UIs over the same status set, deliberately not merged.** The request book's "Callback queue" tab is a persistent, always-available filtered view (`status = received`) for whenever staff have a moment; the Daily Request Review screen is a forced, one-at-a-time walk through everything still open (`open` + `on_po` + `received`), triggered by the alarm, meant to guarantee nothing sits untouched for a full day. There's no separate "reviewed" flag in the schema — a "review" is just a human looking at a card and either acting on it or explicitly hitting skip, not a new status.
- **Daily review alarm is honestly scoped to a browser tab, not faked as the doc's fuller Android/WhatsApp vision.** Section 6B.5 describes a foreground-service alarm (needs the Android app — not built yet) and WhatsApp escalation after repeated unreachable attempts (M8). What a web tab can actually do: poll every 15 minutes while open, and — only when there's a genuinely nonzero count — show a banner, fire one browser `Notification`, and beep on a loop (generated via Web Audio, no shipped audio asset) until reviewed or snoozed for the day. **Known, disclosed gap**: most browsers won't play audio before the page has seen a user gesture, so the very first alarm of a session can be silent until the user clicks anything on the page — a browser autoplay-policy limit, not something fixable from inside a web tab. None of this fires if the tab isn't open; the real always-on version is still an M11+/Android-app problem.
- **POS's "Customer arrived — bill now" hand-off has no product-by-id lookup to lean on** — there's still no `GET /products/:id` in this build — so it re-runs the same unified search the rest of POS already goes through, keyed on the request's product name, and matches the result back by id. If that search doesn't turn up the exact product (unlikely, but possible for a name that doesn't self-match well), the UI says so and lets staff add the line manually rather than silently failing.
- **StrictMode double-invoke caught a real bug, not just a dev-mode nuisance**: the fulfilment-preload effect in `PosPage` was pushing the reserved line onto the bill twice on the very first render, because it had no idempotency guard — React 18 StrictMode's intentional double-invoke of effects in development surfaced it immediately. Fixed with a ref keyed on the request id, which also makes the effect correctly safe outside StrictMode against any future re-render that doesn't actually change which request is being fulfilled.

## Post-M5 fixes (owner-reported, on the printed bill)

Three real gaps in the receipt, all found by the owner actually looking at a printed bill rather than by re-reading code:

- **Customer mobile number** was silently omitted from the receipt whenever no customer *name* was captured (it was nested inside the name line's parentheses, so no name meant no phone either). Now prints on its own `Mobile: <number>` line whenever a phone was captured, independent of whether a name was given.
- **Rack/bin location** wasn't on the bill at all — the bill-detail query never joined `bins`, and the doc didn't specify whether a customer bill should show it. Asked; the owner wants it there. Now each line prints `Rack <bin_code>` alongside batch/expiry/HSN, sourced from that specific sub-line's actual bin (so a multi-batch split sale shows the correct rack per sub-line, not one rack for the whole item).
- **Discount** only ever checked the bill-level discount field, so a discount applied per item in POS (%, ₹, or target-price mode on that line) printed nowhere on the bill even though the customer was genuinely charged less — reproduced with a real 10% line discount showing `bill_discount_value: 0` and no discount row anywhere. Fixed to show each line's own discount inline and sum line + bill-level discounts into one always-accurate summary row.

## M6 — cycle counts, expiry audit, damage/write-off, statutory reports

- **Cycle count bin selection is four ranked candidate pools, round-robined, not one combined score.** Section 9 lists "highest value, highest movement, longest since last counted, or flagged variance history" without a weighting formula, so this doesn't invent one — `selectBinsForCycleCount` draws one bin at a time from each pool in turn, skipping bins already picked today, until the day's target count is reached. `apps/api/src/domain/cycle-count-selection.ts`.
- **A cycle count task's `system_quantity_base_units` is a snapshot taken when the task is generated, not re-read live at counting time.** Reasonable for same-day counting (the whole premise of "daily"), but if a task sits pending across a stock movement, the variance reflects drift since generation, not since the actual count moment. Not flagged as a bug — there's no stated requirement for live re-snapshotting, and the alternative (re-checking at submit time) would defeat blindness by exposing timing signals.
- **Cycle count approval is the only thing that ever changes stock from a count** — writes one `adjustment` ledger row per line with a nonzero variance, only on approval; rejection leaves the system quantity standing, i.e. the count is treated as disputed, not authoritative. Verified live: an escalated ₹5,700 variance was rejected with zero ledger rows written and stock unchanged; a smaller ₹10 variance was approved and correctly adjusted stock down.
- **Variance escalation thresholds (₹500 → Manager, ₹2,000 → Owner) are seeded defaults, not stated numbers** — Section 9 says "above a threshold" twice without giving either value. Same treatment as every other unstated threshold in this build: a reasonable default, owner-editable later, flagged here rather than silently invented.
- **"Move to quarantine" from the expiry audit reuses put-away's task/confirm machinery wholesale** rather than writing a new ledger-move path — `reference_type = 'expiry_audit'` on a `putaway_tasks` row, `suggested_bin_id` pointed at whichever active QC bin currently holds the least value. Blocking the batch (`batches.blocked = true`) happens synchronously and immediately stops FEFO picking; physically relocating it still needs a human to walk over and confirm, per Section 10.2's own rule that no bin-to-bin move happens silently in the ledger.
- **Write-off requires a physical-stock check that didn't exist until this pass caught it in review**: nothing was validating a write-off's quantity against what's actually in that bin, so a write-off for more than what's there would have silently driven `stock` negative. Added `assertPhysicallyAvailable`, checked against raw `stock` (not `sellable_stock` — a blocked/quarantined batch must still be write-off-able) both at request time and again at approval time, since stock can move while a high-value write-off sits in the approval queue.
- **Write-off photo evidence lives on local disk** (`UPLOAD_DIR`, default `./uploads`), not object storage — no S3/GCS is configured for this pilot's single-VPS deployment. Fine for one instance; **move this before ever running more than one API instance**, since local disk won't survive a redeploy or a second replica. Filenames are always server-generated UUIDs, never derived from the uploaded name, so there's no path-traversal surface on write or read-back.
- **GSTR-2A/2B reconciliation (Section 10A.1) deliberately not built.** It needs a real downloaded 2A/2B export to parse against, and guessing at that file's column layout risked shipping something that silently mismatches the government's actual format — worse than not having it. Revisit once a real sample export is available.
- **GSTR-1's B2B and B2C-large tables are always empty today, honestly, not a bug**: no counter sale in this build captures a customer GSTIN (Section 6A never asks the biller for one), and every counter sale is intra-state by the M4 `splitCounterGst` decision, so there's no interstate B2C case either. Both queries are real and correctly shaped, not hardcoded `[]` — they'll start populating themselves the moment a GSTIN field exists on a sale.
- **GSTR-3B's "ITC reversed" is always ₹0 today** — this build has no field anywhere to mark a recorded purchase as ineligible for input credit (blocked credit, personal use, etc.), so every purchase is treated as fully eligible until that concept exists. Shown as its own zeroed line on the working rather than folded silently into the total, so the gap is visible to whoever reviews it.
- **HSN summary's UQC column is `products.base_unit` as-is** (tablet/ml/unit…), not mapped to the GST portal's formal UQC code list (NOS/KGS/LTR…) — that mapping doesn't exist in this build. Same "for accountant review" caveat as the rest of Section 10A.
- **A real negative-stock row was caught by this milestone's own new exception report**, not manufactured for the demo: leftover from earlier ad-hoc curl testing in an M5 session, `stock` had a batch sitting at `-1`. Left in place deliberately (the ledger is append-only — there's no legitimate way to edit it away) and used to verify `negative-stock-exception` actually surfaces a genuine anomaly, not just a synthetic one.
- **Nav bar is now 13 tabs wide** with M6's four additions. Still flat, matching the pattern since M2 — worth revisiting (grouped/dropdown nav) once M13's full console parity pass starts adding more, but not a blocker for any milestone up to now.

## M7 — trade practices: prescribers, margin/scheme tracking, credit customers, pack-aware reorder, vendor comparison

- **Prescriber master reuses M2's trigram-search pattern wholesale** — `pg_trgm` was already enabled and already proven for product/salt search, so prescriber autocomplete (Section 9A.1: "costs the biller one or two keystrokes") is the same `%` similarity + `ILIKE` combination, not a new search technology. `sale_prescriber_details.prescriber_id` is a nullable FK added alongside the existing free-text prescriber fields — a biller can still type a name manually for a one-off prescriber who's never been added to the master, and that free text is preserved even when no `prescriber_id` match exists.
- **Margin reporting's "category" is `schedule_category`** (OTC/H/H1/X/…), not a separate merchandising taxonomy — there's no other categorical field on a product in this build, and inventing a merchandising-category system wasn't asked for. Flagged in the UI itself (`MarginReportsPage`'s hint text), not just here.
- **Vendor-level margin attribution is best-effort, on purpose**: a batch's vendor comes from whichever `purchase_invoice_line` first brought it in; a batch with no such line (non-GST `stock_received`, opening stock) is grouped under `"Unknown / non-GST source"` rather than silently dropped, so the gap in vendor-level reporting stays visible instead of quietly undercounting.
- **Margin reports (and only margin reports) are Owner-only, not Owner+Store Manager** like the rest of M7's screens — same "absent, not blanked" cost-visibility bar used everywhere else this build shows cost data (POS's per-line margin, purchase entry's rates). Prescriber, customer-ledger, and vendor-comparison screens are Owner+Store Manager, matching the roles already trusted with billing and purchasing.
- **Credit customer family grouping is one level of self-reference** (`customers.account_customer_id` → another customer's id), not a separate account/member junction table. `updateCreditSettings` explicitly rejects a customer being their own account holder and rejects chaining (an account holder can't itself be someone else's family member) — Section 9A.4 describes "several members billing to one account," not nested chains, so nesting wasn't built.
- **Payment allocation is written once, at record time, not lazily recomputed.** `recordPayment` walks a customer's outstanding sales oldest-first (or a chosen sale first, then oldest-first for the remainder) and writes one `customer_payment_allocations` row per sale it touches, immediately. Ageing and balance queries never replay payment history — a sale's outstanding is always `credit_tendered − SUM(allocations)`, a straight read. Section 9A.4's own phrase, "allocated to specific bills or oldest-first," is handled by which sale gets pushed to the front of that ordering, not by two different code paths.
- **Real bug caught during this milestone's own live verification, not left in**: `createSale` had no upper bound on credit tender at all — cash overage becomes change, but credit had no equivalent concept, so tendering more credit than the bill's total silently inflated the customer's permanent balance by the difference. Caught with a real test sale (tendered ₹1100 credit against a ₹291.20 bill; balance was wrongly carrying the full ₹1100). Fixed with two new checks in `apps/api/src/repo/sales.ts`: a credit sale now requires a customer phone (`credit_requires_customer`), and credit tendered can't exceed the grand total (`credit_tender_exceeds_total`, ₹0.50 rounding tolerance). The corrupted test row was hand-corrected via SQL — justified only because `sale_tenders`, unlike `movement_ledger`, has no append-only trigger, and the bad row was purely this session's own test-data mistake, not a real transaction.
- **Vendor minimum order pack is one default field per vendor** (`vendors.default_min_order_pack_units`), not a product-vendor junction table. Section 9A.7 says "round the suggested order quantity up to the vendor's minimum order pack" in the generic singular — a real per-product MOQ table is a bigger, unstated data-entry burden this milestone doesn't invent. `suggestedPurchaseOrderLines` rounds up and flags `moqRoundedUp` on the line so the UI can show why a quantity isn't the raw shortfall number. Verified live: a shortfall of 122 units against a 50-unit MOQ correctly rounded to 150.

- **Real bugs caught and fixed during this milestone's own live verification, not left in** (five, the most of any milestone so far — a good argument for why "verify against the real system" stayed the standing rule even under a live-API blocker):

Fixed by also requiring `raw_extraction IS NOT NULL`. Caught by literally re-uploading the same test file twice.

Fixed to accept both statuses, skipping the raw-vs-final diff (there's nothing to diff) when there was no extraction to correct against.
  - The corrected-fields diff was written via `JSON.stringify(correctedFields)` even when `correctedFields` was JS `null`, which serializes to the *string* `"null"` — a jsonb `null` value, not a real SQL `NULL`. That would have passed `IS NOT NULL` in the vendor accuracy report and then crashed reading `.totalFieldsExtracted` off of it. Fixed to pass a real `NULL` parameter instead of a stringified one.

Classic stale-closure bug — caught only by actually watching the screen in a browser, not by reading the diff.

- **Vendor is picked before extraction runs, not guessed from the extracted vendor name afterward.** The brief doesn't dictate the order; picking it first (same UI pattern as manual purchase entry) means `vendor_product_aliases` lookups can run in the very same request that returns the extraction, instead of a two-step "extract, then guess vendor, then re-run matching" flow. - **Failed-delivery returns are their own table (`delivery_return_tasks`), not a reuse of `putaway_tasks`.** A put-away task assumes stock is already sitting in a real staging bin; a failed delivery's stock is physically in the rider's bag until scanned back in, so there is no `staging_bin_id` to point at. The shape is deliberately the same as put-away's scan-to-confirm pattern (require the real bin code typed/scanned, never accept the suggestion blindly) — just a dedicated table instead of forcing a case `putaway_tasks` wasn't built for.
- **A failed delivery cancels the sale immediately but defers the stock movement until a human scans each item back into a bin** (Section 8: "must be scanned back into their bins, not silently restocked"). `markDeliveryFailed` sets `sales.status = 'cancelled'` and creates one `delivery_return_tasks` row per `sale_line` in the same transaction; the `movement_ledger` "sale_return" row is only written by `confirmDeliveryReturn`, once a real bin code is confirmed. Verified live: stock at the confirmed bin increased by exactly the returned quantity only after the scan-confirm step, not at the moment of marking the delivery failed.
- **A new `cod_pending`-settling step, not a new tender type.** M10 already added `cod_pending` for the pack-time invoice; `markDelivered` here just updates that same `sale_tenders` row (`tender_type` → `cash`/`upi`, `amount` → what was actually collected) rather than inserting a second tender row — one row always represents "how this bill was actually paid," whether that's known at pack time (POS) or only at delivery (this milestone).
- **End-of-shift cash reconciliation is a new `rider_cash_reconciliations` table, not a reuse of `day_close`.** Same shape and same "server-computed expected, never trusted from the client" principle as the counter's day-close (Section 6A.5), but `day_close` is keyed uniquely on `business_date` alone (one closure for the whole counter); multiple riders closing the same day independently needed a `(rider_id, business_date)` key instead. Riders close their own shift (Section 3: rider role can do "end-of-shift cash reconciliation" themselves); Owner/Store Manager get a read-only list across all riders for variance review. Verified live with a genuine mismatch (expected ₹11.20, declared ₹10.00 → variance −₹1.20, correctly recorded and visible on the Owner's list).
- **Two more Section 8 items are genuinely deferred, not missed**: the internal "Failed delivery alert" (Section 12A.3) waits alongside every other internal WhatsApp trigger, none of which have been built since M8 chose not to scope them there either. "Navigate" (Section 3's rider permission list) isn't a feature this build can add — it's an external maps app the rider already has; no in-app turn-by-turn was attempted.
- **`GET /orders/:id` now also accepts the rider role, but with an ownership check role alone can't express** — a rider may only fetch an order actually assigned to them (`order.rider_id === req.auth.sub`), checked explicitly in the route handler rather than folded into `requireRole`, since every other role check in this build is a pure role check with no per-row ownership condition.

## M12 — Section 11 / 6A.9: offline mode and sync ledger, POS offline-first

- **Scoped to exactly what Section 6A.9 asks for — offline billing at the counter — not every offline flow Section 11 lists.** Picking, packing, cycle counting, and put-away are named in Section 11 too, but this milestone's own build-order bullet is "offline mode and sync ledger, POS offline first." Those other screens reuse the same outbox/sync mechanism this milestone builds (IndexedDB queue, idempotency key, `sync_conflicts` escalation) once they're wired to it — a named next step, not a silent gap. Flagged again in README's Status section so it isn't mistaken for finished offline coverage.
- **Bill numbers are reserved in small blocks (`bill_number_blocks`, default size 5, a seeded setting `offline_bill_number_block_size`), not drawn one at a time from the real counter while offline** — there's no way to safely advance a single shared counter from a disconnected device. This trades away M4's "gapless by construction" guarantee for genuinely offline devices: an abandoned block (device goes offline, never sells through its 5 reserved numbers, and is later wiped or replaced) leaves a bounded, disclosed gap in the bill sequence — a real, accepted tradeoff of allowing offline billing at all, not something hidden. `reserveBlock` atomically advances the same counter `reserveNumber` uses, so online and offline numbering never collide or double-issue.
- **Idempotency is enforced at the `createSale` level, not just in the `/sync/sales` route.** `createSale` now checks for an existing sale by `idempotencyKey` before doing anything else and returns it as a no-op if found, so a retried sync (network flake mid-request, a rider's device double-firing the same queued entry) can never double-create a sale. Putting the check in `createSale` itself, rather than only in the sync route, means any future caller gets the same safety for free without having to remember to add it.
- **Any sync failure that isn't a plain network error becomes a durably-logged `sync_conflicts` row, never a silent auto-resolve.** Section 11's own framing — offline conflicts get escalated to the Owner, not resolved behind their back — is taken literally: `/sync/sales` catches `ValidationError` (insufficient stock, etc.), records it via `recordSyncConflict` (upserted on `idempotency_key` so a repeat sync attempt doesn't spam duplicate rows), and returns 409. The web outbox treats any real server response (including a conflict) as "stop retrying this one, it's recorded" — only a genuine network failure leaves an entry queued for another attempt. Verified live via curl: an intentionally oversized offline sale correctly produced a `sync_conflicts` row, listed on `GET /sync-conflicts`, and was resolvable via `POST /sync-conflicts/:id/resolve` with a resolution note.
- **Offline FEFO (`allocateFefoOffline`, mirroring `domain/fefo.ts`) deliberately skips the near-expiry pick-block-days exclusion the server applies.** Every offline pick is recorded through the same manual-batch-override mechanism (`SaleLineInput.manualBatchId`) Section 6A.2 already defines for POS batch overrides — and a manual override already bypasses that exclusion when billing online today, so this isn't a new gap, just the existing override behaviour extended to the offline path. Pinning the offline-chosen batch via `manualBatchId` also means sync-time replay through `createSale` can never silently pick a different batch than what was actually shown on the offline device.
- **The offline product cache (`GET /pos/offline-snapshot`) is built from the same `sellable_stock` view and joins `allocateFefo` itself reads from** — guarantees the offline cache reflects the same data shape a live pick would use, not a separately-maintained projection that could drift from the real allocation logic.
- **Two real bugs caught and fixed before/during live verification**:
  - `queueOfflineSale`'s discount split silently dropped discount on any line FEFO-split across 2+ batches — the first draft only applied `line.discountValue` to the sub-line whose quantity matched the full requested quantity, so a split line kept its full price on every other sub-line. Caught during implementation review, not by a failing test; fixed to distribute proportionally by `shareOfQty`, mirroring `createSale`'s own split logic exactly.
  - The offline receipt's `grandTotalEstimate` omitted GST entirely — it summed raw taxable value with no tax added, showing ₹90 for a sale whose real GST-inclusive total was ₹100.80, a ~12% gap on a screen sitting right next to POS's own GST-inclusive online total. Caught by comparing the offline-displayed total against the server-confirmed total of a prior synced sale (DPS-000059, confirmed via `psql` at ₹100.80). Fixed to compute a real per-line taxable value and tax amount using each product's actual cached `gstRate` (more accurate than the online screen's own hardcoded 12%-estimate display) — reverified live: a fresh offline sale (DPS-000069) showed the correct ₹100.80 offline, then synced and confirmed server-side at the same ₹100.80 via `psql`.
- **Sync conflicts get their own Reports tab (`SyncConflictsTab`)**, not folded into an existing report, since "surfaced to the Owner" (Section 11) needs somewhere an owner actually looks — filterable by status (open/resolved/all), with a required resolution note before a conflict can be marked resolved, matching the existing pattern of requiring a reason on other override/exception actions in this build (write-offs, cycle-count variance).
- **Honesty about what "offline" means stays consistent with M5's alarm and M11's GPS pings**: this is real IndexedDB persistence and a real background-agnostic outbox, but sync only actually triggers on the browser tab's own `online` event — there's no true background sync without a native app (Section 13's Android/Expo app, still not scaffolded). A device that goes offline, is closed, and reopened still has its queued sale intact (IndexedDB survives a tab close) and syncs the moment it's next online with the tab open — just not while the tab isn't running at all.
- **Owner asked whether a "reorder book" — sales, purchases, and closing stock per SKU over a date range in one screen — exists, and if not, to build it.** Checked: it doesn't. The existing reports (statutory registers, margin, inventory, exceptions) don't include this view, and it isn't named anywhere in the build spec by this shape either — Section 9A.7's "pack-aware reorder levels" only covers computing a reorder *level* from sales velocity for the existing low-stock/PO-suggestion list, not a sales-in/purchases-in/closing-stock ledger report. Asked whether to build it now, out of sequence; answered: wait, defer to M13 (Owner web console completion / reporting). Not built this milestone — noted here so it isn't mistaken for an oversight.

## M13.1 — Section 10.2: Staff & roles

M13 (Section 10.2's full web read/write parity, plus reporting/SQL console and WhatsApp inbound) is by far the largest milestone in the build order — too large for one pass. It's being built as a sequence of chunks (M13.1, M13.2, ...), each schema/domain/routes/UI/verify/push on its own, same discipline as every prior milestone, rather than one enormous uncommitted change. M13.1 is Staff & roles, picked first since M11 already left rider onboarding as a stub waiting on it.

- **Per-user permission overrides are enforced by extending `requireRole(...)` itself, not by adding a parallel authorization system.** `permission_key` reuses the exact role-name strings already passed to `requireRole` everywhere in the codebase — granting a user an override for `'owner'` means every existing `requireRole("owner")` call now also passes for them, with zero changes to any of the dozens of route files that call it. The override check only runs on the way to a 403 (role already matching is the common case and pays no extra query), and is skipped entirely for an impersonated session — an override belongs to the real account, and stacking it with Section 3's separate impersonation role-swap would make "what can this session actually do" unauditable. Verified live: a store_manager granted an `owner` override got a real 200 from `GET /users` (owner-only); revoking it brought back a real 403 — this is enforcement, not a UI-only flag.
- **"Delete a user account" (Section 10.2) is implemented as suspend, not a hard `DELETE`.** A real delete would orphan every foreign key this user shows up on as an actor — `created_by` on orders, `served_by`/`approved_by` on sales and write-offs, the entire audit trail this build is built around. Suspend already exists as the account-disable mechanism (blocks login with `account_suspended`, verified live); "delete" in the UI calls the same endpoint. A judgment call, not a silent scope-narrowing — Section 10.2's own words ("delete user accounts") don't fit an audit-trail-preserving system literally, and this is the one interpretation that doesn't contradict everything else this build already promises about append-only history.
- **The per-user activity log ("every action that user has taken") is populated by one generic Fastify `onResponse` hook (`plugins/activity-log.ts`), not by adding a log call inside each route handler.** Hand-instrumenting every route would make "every action" a promise that quietly erodes the next time someone adds a route and forgets the log line — the hook makes it structurally true instead. Only mutating methods (POST/PUT/PATCH/DELETE) are logged as activity; GET requests are excluded from `activity_log` on purpose — logging every page load and poll would bury the real audit trail in noise nobody asked to see, and Section 10.2 talks about actions taken, not screens viewed.
- **"Who is logged in now" / "hours logged this week" (Shift and roster view) are honest approximations, not a real clock-in/out system** — this build has no session table at all (stateless JWT, a stack choice from M0/M1), so there's no ground truth for "logged in." A separate `user_last_seen` upsert, touched on every authenticated request including GETs, drives "online now" (active in the last 15 minutes, matching Section 10.4's web idle timeout). "Hours this week" sums each day's span between first and last recorded *activity_log* action over the last 7 days — it undercounts genuinely idle-but-logged-in time and can't see a day with only one action. The Roster tab says this in plain text above the table, same honesty pattern as M5's alarm, M11's GPS pings, and M12's offline sync.
- **Rider onboarding's "active/inactive status" reuses the existing `users.status` (active/suspended) rather than a second, possibly-contradictory flag.** `rider_details` (vehicle) and `rider_documents` (license/RC/ID photos, reusing the exact write-off photo-upload pipeline — images only, local disk, server-generated filenames) are new, additive tables keyed off the same `users.id` M11 already used for rider assignment.
- **Staff & roles is owner-only across every write**, including rider onboarding fields that are store_manager-writable everywhere else in the API (e.g. `PUT /riders/:id/details` still checks `owner`/`store_manager` for the field-editing convenience, but every account-shaping action — create, role change, PIN reset, permission grants, suspend — is owner-only). This is the one module that can mint accounts and hand out `owner`-level access, so it's the one place a `store_manager` grant would be a privilege-escalation path rather than a convenience.

## M13.2 — Section 10.1: manual-override infrastructure for scan-backed actions

- **Put-away confirmation (M3) already did this correctly and unconditionally** — `source: 'web_manual'`, a mandatory reason code, the bin code typed in full, since there's still no separate scanning client. This milestone extends the exact same reasoning to Section 10.1's other four listed actions (pick confirmation, packing verification, rider handover, cycle count entry), which hadn't been wired up yet despite comments in two of those files (cycle-counts, order-picking) already flagging the gap.
- **The reason code is captured once per session (order, or cycle-count task), not once per line.** Section 10.1 asks for a mandatory reason on "confirming a pick against a batch" and "packing verification," but a delivery order can have a dozen-plus lines — repeating the same justification that many times fights Section 6A.1's speed targets for no real audit benefit over asking once, at the point the whole picking/packing session for that order is confirmed complete (`complete-picking` / `complete-packing`). This mirrors put-away's own granularity: one reason per put-away *task* (its natural atomic unit), not per scan within it. Rider handover already was a one-shot per-order action, so it just gained the same two fields directly.
- **Two different ways of surfacing "why," matched to whether the action has a ledger row of its own at that moment.** Pick confirmation and rider handover never move stock (nothing is deducted at pick time; a handover doesn't touch inventory), so they get a row in a new `web_manual_overrides` table instead. Packing verification and cycle-count-approval *do* eventually write a real `movement_ledger` row (the pack-time sale; the count's approved adjustment) — those get `source = 'web_manual'` directly on that row, same as put-away, with `web_manual_overrides` reserved for actions with nothing to tag. Cycle count entry is a special case: the reason is captured at `submitCount` time, but the ledger row is only written later at `reviewTask` (approval) — carried across that gap via two new columns on `cycle_count_tasks` (`count_reason_code`, `count_note`) that `reviewTask` reads when it writes the adjustment row.
- **Cycle count entry gained a real "confirm you're at this bin" step that didn't exist before** — `submitCount` previously trusted whichever `taskId` the client sent with no physical check at all, despite Section 10.1 explicitly listing cycle count entry as needing "the user to type the bin code / batch number in full." Now the counter must type the bin's own code (matching the task's actual bin, never pre-filled), or the submit is rejected with `bin_mismatch` — verified live with a deliberately wrong bin code.
- **The Manual Override report (`GET /reports/manual-overrides`) unions both sources** — `movement_ledger` rows tagged `source = 'web_manual'` and `web_manual_overrides` rows — into one chronological list, rather than making the Owner check two screens. Verified live: a full order lifecycle (pick → pack → rider handover) plus a cycle count entry and approval all appear correctly, alongside the historic put-away rows from earlier milestones.
- **No Owner-only gate or Manager-access settings toggle was added, deliberately extending the M3 put-away precedent rather than contradicting it.** Section 10.1 frames these as "Owner-only by default; Manager access... is a settings toggle," but that assumes a working scanning client (the Android app) exists as the normal path and web is a restricted fallback. Since the Android app still doesn't exist (Section 13, unbuilt), web is the *only* way any of this work happens today — gating pick/pack/handover/cycle-count-entry to Owner-only would lock picker_packer and rider staff out of their own jobs. Every action stays open to whichever role already performs it (unchanged from before this milestone); only the Manual Override *report* (viewing, not doing) is Owner/Store-Manager, matching every other report in this build.
- **A real bug caught during live Playwright verification**: the new Manual Override report screen crashed (`Cannot read properties of null (reading 'slice')`) on the pre-existing put-away rows from earlier milestones, which have no `reference_id` (movement_ledger's `reference_type`/`reference_id` are nullable and those old rows predate this report). Fixed by guarding the render (`r.referenceId ? r.referenceId.slice(0, 8) : ""`), reverified with a clean Playwright pass.

## M13.3 — Section 10.2: Inventory parity

- **"Move stock between bins" reuses M3's put-away pipeline wholesale, rather than building a second stock-movement mechanism.** Section 10.2's own wording ("creates a put-away task for floor staff to physically execute and confirm, rather than silently moving it in the system") describes exactly what `putaway_tasks` + `confirmPutaway` already do — a new `createBinTransferTask` just inserts a task with `reference_type = 'bin_transfer'` and the *current* bin as `staging_bin_id` instead of a receiving dock, then the existing scan-to-confirm flow (zone-forcing hard blocks, M13.2's mandatory web-manual reason code, everything) takes over unchanged. **This is also the bin-to-bin migration the Owner asked about before M11 and was explicitly told to wait for M13** — verified live end to end: moved 20 units of a real batch from one bin to another, confirmed it appeared on the existing Put-away queue (not a new screen), confirmed the destination bin held 0 before and 20 after only once the move was scan-confirmed, and confirmed the source bin's stock stayed untouched until that same moment.
- **Quantity correction reuses movement_ledger's existing `adjustment` movement type** (same one cycle-count-variance approval already writes) — no schema change needed for it. **Batch-number, expiry, and MRP corrections can't go through movement_ledger at all** — its `quantity_delta` column has a hard `CHECK (quantity_delta <> 0)`, and none of those three fields represent a quantity change. A new `batch_corrections` table (field/old_value/new_value/reason/note, append-only) is the audit trail for those instead — the literal "writes a ledger row" instruction doesn't fit a non-quantity edit, so this is the interpretation that keeps "never an in-place overwrite" true without contradicting the schema's own constraint. Verified live: MRP corrected from ₹30 to ₹32 to ₹33.50 across two separate corrections (one direct, one via bulk CSV), each producing its own `batch_corrections` row with the real old/new values.
- **Inventory correction reason codes are a distinct set from Section 10.1's web-manual reason codes** (`physical_recount`, `data_entry_correction`, `damage_pending_writeoff`, `system_error`, `other`) — Section 10.1's set (`scanner_unavailable`, `remote_correction`, `device_failure`, `training`) answers "why did you type this instead of scanning," which doesn't fit a quantity/MRP/batch correction at all (there was never a scan to substitute for). Block/unblock reuses the existing `batches.blocked`/`blocked_reason` columns from M0/M1 (already respected by FEFO allocation, already set one way by M6's expiry-audit move-to-QC action) rather than adding new ones — this milestone just exposes a generic Inventory-screen toggle for it, for any reason, not just near-expiry.
- **Bulk CSV import: preview and commit both recompute the diff fresh from current DB state — nothing is cached server-side between the two calls.** The client just re-sends the same CSV text it already showed the user for commit; there's no preview-token table to create, expire, or worry about going stale if the DB changes between preview and commit (commit re-validates against current state regardless). A minimal hand-written CSV parser (comma-split, no quoted-field support) replaces the earlier plan to add a dependency — documented as a real, accepted limitation (product/batch/bin identifiers in this build don't contain commas) rather than silently mishandling one that did. **Bulk bin reassignment applies the same "never silently move it" principle as the single move-stock action**, even though Section 10.2's text only restates that qualifier under the single-item bullet — creating N put-away tasks per CSV row rather than writing the movement directly, for consistency with the rest of this build's treatment of the same underlying action regardless of how many rows triggered it.
- **CSV rows are matched by product name + batch number** (both already how staff identifies items everywhere else in this build — typed batch numbers "as printed" is the established pattern since M6's cycle counts), not by an internal UUID nobody would type into a spreadsheet. There's no dedicated SKU/barcode column reliable enough to require in a CSV (barcode is nullable on `products`), so an unmatched or ambiguous row is flagged `not_found` in the preview and simply skipped at commit — never guessed at.
- **A near-miss caught before it shipped**: `apps/api/src/lib/csv.ts` already existed (Section 10A's CSV *export* helper, `toCsv`, used by every statutory report's download button) — an early draft of this milestone's CSV *import* parser overwrote that file outright instead of adding to it, which would have silently broken every report export. Caught by a `tsc` compile error (`toCsv` no longer exported) before the servers were even restarted, not by a runtime failure — both functions now live in the same file.

## M13.4 — Section 10.2: Product master parity

- **Substitute-group management is a straight override of the one join key every consumer already reads, not a parallel structure.** `substitute_group_id` has been a pure deterministic function of composition+strength+form since M2 (`substituteGroupKey`), with no manual override path — Section 10.2 explicitly asks for one ("this is where you will do most of your generic-substitution setup"). A new screen lets the Owner/Manager either link a product to another product's existing group or split it into a brand-new group of its own; both are a single `UPDATE products SET substitute_group_id = ...`, and every consumer (search grouping, order-picking's short-pick substitute lookup, the request-book's substitute finder) picks up the change automatically since they all just join on that column — no new consumption logic anywhere. A new `product_group_changes` audit table logs a required note (not a fixed reason-code taxonomy) for each change, since linking or splitting substitutes is a pharmacist's clinical judgment call, not an error being corrected — the two other M13 audit tables (`batch_corrections`, `web_manual_overrides`) both use fixed reason codes for genuine corrections/exceptions; this one is deliberately different.
- **Bulk CSV import of the product master supports both create and update, matched by (name, manufacturer)** — but an update row is deliberately restricted to the same fields the single-product edit screen already allows (barcode, allow_loose_sale, status), never form/schedule_category/HSN/GST rate/pack size. Those touch statutory and historical-sale data (an HSN/GST change on a SKU with existing invoiced sales would misrepresent history if applied retroactively without more care than a spreadsheet row can express), and there's no single-product edit path for them either — bulk import doesn't get more power than the interactive screen it mirrors. A create row does get the full field set, including composition (required — `createProduct` has always required at least one salt, so a bulk-created SKU can't skip it), using a pipe/colon sub-format (`SaltName:Strength|SaltName2:Strength2`) inside the one CSV cell.
- **Bulk-created products skip the single-entry "possible duplicate" soft-block** that interactive product creation shows (Section 6B.2's "warn if an existing SKU shares composition/strength/form"). That warning exists to catch a human about to type a near-duplicate by hand; a batch import has already been reviewed once in the preview-diff by the time it commits, and re-surfacing per-row interactive warnings mid-batch would defeat the point of a bulk tool. If a bulk import creates a genuine composition duplicate, it silently gets its own correctly-computed substitute group like any other product — visible and fixable afterward through the new substitute-group screen, not blocked at import time.
- **Product barcode label-sheet PDF generation was a genuine gap, not just an unclear README line.** M2's README bullet ("barcode assignment and printable label sheet generation") turned out to only ever have been built for bins (`/bins/label-sheet`, M2) — product barcode labels had no PDF endpoint at all until now. `buildProductLabelSheetPdf` reuses the exact same A4 sticker-sheet layout and QR-encodes-the-scanned-value convention as the bin version (this build has never had a real 1D barcode renderer, for bins or products) — both functions now share `domain/label-sheet.ts`. A product with no barcode assigned is silently skipped from the sheet, not printed with a blank or fake code.

## M13.5 — Section 10.2: Bin master parity

- **Rename and retire were already technically possible via `PATCH /bins/:id` since M2** (`code` and `status` were always updatable columns) — but with no safety check, retiring a bin that still held recorded stock would silently leave that stock invisible on the bin master while FEFO and the stock view kept happily allocating against it. `updateBin` now hard-blocks `status: 'retired'` whenever `SUM(quantity_base_units) > 0` at that bin, same character as the cold-chain/SH1 zone-forcing rule (Section 6.6) — a physical-consistency issue, not a judgment call to soften. Verified live: retiring a bin holding 50 units correctly 409s with the exact quantity; retiring the same bin after its stock was moved out and confirmed elsewhere succeeds.
- **"Merge bins" queues one put-away task per (product, batch) currently in the source bin — it never combines the two bins' stock records directly.** Section 10.2's own parenthetical for the single-bin move action ("creates a put-away task... rather than silently moving it in the system") is applied here too, for the same reason M13.3 applied it to bulk bin reassignment: a merge is still a physical relocation that needs a floor staffer to actually walk the stock over and scan-confirm it, whether it's framed as "move" or "merge." Because retiring a bin already hard-blocks while it holds stock, this composes for free: a merged-from bin literally cannot be retired until every one of its queued tasks has been scan-confirmed at the target — verified live end to end (merge → task appears on Put-away, unconfirmed → retire still blocked → confirm the task → retire now succeeds).
- **Visual rack map reuses the `capacity_score` column bin creation has always set (default 100, Owner-editable) as the fill-percentage denominator**, rather than inventing a new field — it was already there, already exposed via `updateBinSchema`, just never displayed anywhere. Fill percentage is deliberately *not* clamped to 100 in the displayed number (only the heat-map colour is clamped, via `Math.min(fillPercent, 100)`) — a bin genuinely holding more than its nominal capacity (visible live during verification: one test bin showed 208% after several earlier milestones' verification runs pushed real stock into it) is exactly the kind of thing a re-slotting tool should surface honestly, not hide by capping the number.
- **A real, disclosable gap fixed in passing**: bins created through the API with only a `code` string (the web create form has only ever asked for a code) left `aisle`/`bay`/`shelf_level`/`position` NULL even for a regular-format code like `A-03-B-2` that structurally encodes all four — meaning any bin created via the web console (as opposed to the seed script, which always wrote these explicitly) would have been invisible to the rack map's aisle/bay grouping. `createBin` now parses a regular-format code the same way the seed script always has (`parseRegularBinCode`) and only falls back to explicit fields when given, so this is fixed for every future bin regardless of how it's created — not just newly-surfaced by building the rack map that would have exposed it.
- **Drag-to-reslot on the rack map and "Move stock" on the Inventory screen (M13.3) are the exact same backend call** (`POST /inventory/move-stock`) reached from two different UI entry points — dragging one bin card onto another opens a small picker (pre-filled from the same `GET /inventory/stock?binId=` filter M13.3 already built) for which item and how much, then queues the identical put-away task. No new stock-movement code exists in this milestone at all; everything here — merge, drag-to-reslot, and the retire-block — is built entirely on top of M3's put-away pipeline and M13.3's Inventory endpoints.

## M13.6 — Section 10.2: Orders parity

- **"Manual creation" and "full order list, filterable and exportable" were already-existing or nearly-existing capabilities, not new ones.** M10's `NewOrderForm`/`POST /orders` has supported staff-entered orders (catalogue lines, free text, images, all mixed on one order) since Section 7A was first built — nothing new was needed there. The list was new: `listAllOrders`/`GET /orders` (status/date-range/search filters, `?format=csv` via the same `toCsv` helper Section 10A's statutory reports use) plus a new "All orders" tab, reusing the existing `downloadFile` client helper unchanged.
- **"Edit pre-pick" (add/remove line, change quantity, substitute) needed exactly one new backend surface, not three.** `POST /orders/:id/catalog-lines` (add a fully-resolved catalogue line directly — no unstructured-review round-trip) and `DELETE /orders/:id/lines/:lineId` are new; quantity-change and substitution both reuse the M10 `POST /orders/:id/lines/:lineId/resolve` endpoint used for resolving unstructured review lines, since it has no order-status gate and already does exactly what's needed — only the web-side `disabled` gating needed widening (from `received`/`under_review` only, to the full pre-pick window `received → under_review → quoted → customer_confirmed → awaiting_prescription`), plus fixing the `action` sent (`substitute` vs `match`, based on whether the line already has a `product_id`) so re-matching an already-matched line is correctly recorded as a substitution rather than silently overwritten. Both new endpoints hard-block once an order leaves the pre-pick window — `order_pick_lines` (FEFO-allocated batch/bin) exists from `start-picking` onward, and editing lines out from under an active pick list would desync it.
- **Cancel-with-reversal needed zero new stock-reversal logic.** Stock is never deducted until pack time (`createSale` inside `completePacking`) — FEFO allocation at `start-picking` only pins `batch_id`/`bin_id` on `order_pick_lines`, it writes no `movement_ledger` row. So `cancelOrder` only needs real reversal for the two statuses that already have a `sale_id` (`packed`, `partially_available`) — for those it calls the existing `cancelSale` from M4/M13.3 (Section 6A.7's day-close-blocked, full-reversal cancellation) unchanged; every earlier status is a pure `status = 'cancelled'` flip. Verified live both ways: a `received`-stage order cancelled with no ledger activity at all, and a freshly packed order (fresh sale, open business day) cancelled with the batch's `movement_ledger` gaining a `sale_return`/`sale_cancellation` row and total stock returning to its exact pre-sale figure (67 → 68). A cancel attempt against an order whose sale fell on an already-closed business day correctly 409s with `sale_day_already_closed` — the reused guard rail firing exactly as it does for a normal POS return. `cancelled_reason_code` is a fixed 5-value enum (this is a completed-action classification, same character as `batch_corrections`/`web_manual_overrides`) plus a required free-text note; already-terminal (`cancelled`/`rejected`/`delivered`) and already-dispatched (`assigned`/`out_for_delivery`/`delivery_failed`) orders are both blocked with a distinct error code, the latter pointing staff at the Rider screen's delivery-failure flow instead.
- **Force-reassign-rider is a real audit trail with a required note, not a reason-code enum** — same reasoning as M13.4's `product_group_changes` and M13.5's bin-merge/retire: which rider takes over a dispatched order is a dispatch judgment call (rider called in sick, a delivery is stuck), not a correction being made against a fixed taxonomy. `order_reassignments` (old rider, new rider, note, actor) is new; `reassignRider` in `repo/delivery.ts` only allows it while `orders.status` is `assigned`/`out_for_delivery`, rejects a same-rider no-op, and both the API error text and the web UI say plainly that this only corrects the system record — it does not claim to physically relocate a package already in the original rider's hands. Same honesty pattern this build has kept since M5's alarm, M11's GPS/OTP, and M12's offline sync: never overclaim what the software actually does.
- **Refund initiation is a deliberately inert stub**, per Section 10.2's own parenthetical ("stubbed until the payment gateway is live"). `order_refunds` records amount/reason/requester and starts (and, in this build, stays) at `status = 'requested'` — there is nowhere else for it to go until a real payment gateway exists (Section 14: out of scope, handled by the Owner separately), so no fake "processed" transition was built. The refund section on the order screen stays visible even once an order reaches a terminal status (cancelled/rejected/delivered) — unlike the cancel/reassign controls, which correctly disappear once terminal, a refund already on file for a cancelled order is exactly the record the Owner still needs to see, not something that should vanish along with the rest of the panel.
- **A real UI bug caught by live verification, not code review**: the first draft made the entire `OrderActionsPanel` (cancel, reassign, refunds) return `null` outright for any terminal-status order — which meant a refund already recorded against a just-cancelled order became invisible the moment the cancel completed, since the panel disappeared along with the now-irrelevant cancel/reassign controls. Caught by cancelling a real test order, initiating a refund against it, then reopening the order screen and finding the refund history gone. Fixed by splitting the gating: cancel/reassign controls now check `canCancel`/`showDispatchedNotice` (both false once terminal), while the refunds section has no terminal gate at all. The same pass also found and fixed a pre-existing (pre-M13.6) issue on the same screen — the "needs prescription verification" banner was gated only on `rx_required && !rx_verified`, with no order-status check, so it kept showing on a cancelled order too; it's now also gated on the pre-pick-editable window.

## M13.7 — Section 10.2: Inbound/GRN parity

- **"Create inbound records" was already there; "list/view" was the real gap.** Both `POST /purchase-invoices` (M3) and `POST /stock-movements/stock-received` (M3) have existed since M3 with zero read path beyond querying the DB directly — no list, no detail, no way to look a submitted invoice back up from the web console at all. `GET /purchase-invoices` (filterable by vendor/date/search) and `GET /purchase-invoices/:id` (header + lines + documents + correction history) are new; `GET /stock-movements/stock-received` mirrors it for the non-GST path, reading straight off `movement_ledger` since a stock-received entry has no header/lines split to list separately.
- **"Edit inbound records" is deliberately narrow: invoice header/identification fields only** (`invoice_number`, `invoice_date`, `vendor_id`, `payment_terms_days`), via a new `purchase_invoice_corrections` audit table shaped exactly like M13.3's `batch_corrections` (field/old/new/reason/note). Quantity, rate, and GST fields are explicitly **not** correctable this way — they already feed posted `movement_ledger` rows, a batch's `effective_cost_per_base_unit`, and (once GSTR reports exist for a period) statutory filings; recomputing an already-posted multi-line tax invoice's downstream numbers is a materially different and riskier operation than a batch's MRP correction (M13.3), which only ever touches one denormalized column with no other dependents. A wrong MRP is still fixable — through the Inventory screen's existing batch-correction tool, unchanged, regardless of whether the batch arrived via a GST invoice or a stock-received entry. Stock-received entries get no correction path of their own at all for the same reason: each one is already a plain batch + ledger entry indistinguishable from any other by the time it's saved, so the general-purpose Inventory correction tool already covers it.
- **Invoice document upload reuses Section 6.3's `saveScanPage`/`resolveScanPagePath` helpers wholesale** (`lib/scan-uploads.ts` — local disk, JPG/PNG/WEBP/PDF, server-generated filenames only) rather than writing a second file-storage path. The AI-scan pipeline already photographs the invoice at capture time; the ordinary manual-entry path (still the common case) never did, so a new `purchase_invoice_documents` table (one invoice → many documents, since a scan might be a multi-page PDF or split across two photos) lets that evidence be attached after the fact. Verified live: uploaded a test PDF, fetched it back byte-for-byte identical, and confirmed it lists correctly with uploader/timestamp on the invoice detail screen.
- **The receiving-count variance step closes the exact gap flagged back in M3**: "Section 6.6 mentions invoice-versus-received variance is logged... there's no separate physical-count-at-receipt step distinct from data entry yet." Put-away confirm now accepts an optional `actualQuantityFound`, distinct from the task's `quantity_base_units` (what was invoiced or entered) — only for `purchase_invoice`/`stock_received` tasks, since an internal `bin_transfer` or `expiry_audit` move is relocating stock that was already counted once and has no "invoiced vs. found" comparison to make. When the two differ, a required variance reason code + note (a genuine physical-count discrepancy, not a judgment call — same character as cycle-count variance, distinct in shape from the existing "no scanner on web" reason already required on every web put-away confirmation) produces a `putaway_variances` row and an `adjustment` ledger entry that trues up the staging bin's book quantity to what was actually there *before* the transfer moves anything out — so the destination bin always ends up holding exactly what was physically found, never the originally-recorded figure. Verified live end to end: invoiced 10, found 8 (a 2-unit shortage) — staging correctly zeroed out after the transfer (10 recorded − 2 adjustment − 8 transferred = 0) and the destination bin received exactly 8, not 10. A `bin_transfer` task confirmed with a differing `actualQuantityFound` correctly ignored the override entirely (not variance-eligible) and moved its full recorded quantity, with no variance row created.
- **Variance resolution has no auto-escalation threshold**, unlike cycle-count variance (Section 9's explicit ₹500/₹2,000 figures) — Section 6.6 doesn't specify one, so every variance, regardless of size, sits `open` until a human records a free-text resolution (accepted as-is, vendor credit note requested, written off, whatever actually happened) and only then moves to `resolved`. Verified live: resolving an open variance requires a note, a second resolve attempt on the same variance correctly 409s, and the Owner-facing "Receiving variances" tab lists both states with full detail (expected vs. found, reason, reporter, resolution).

## M13.8 — Section 10.2: Audits parity

- **"Schedule/assign cycle counts" needed almost no new schema — M6 had already carried the `manual` value on `cycle_count_selection_reason` since it was first defined, unused until now.** The daily automatic generator (`generateDailyCycleCountTasks`) only ever targets "today" and only ever picks from its four ranked pools; a new `scheduleManualCycleCountTasks` lets the Owner/Manager pick specific bins directly, for any date (today or upcoming), reusing the exact same task/line/system-quantity-snapshot shape and staying idempotent per (bin, date) the same way the daily generator is. **Assignment itself, `PATCH /cycle-counts/:id/assign`, already existed since M6 — it simply had no UI anywhere.** That was the more surprising gap: the backend supported assigning a counter to a task, but the Cycle Count screen never exposed it. Both a "Today" view (now with an inline assign dropdown on every unassigned pending task) and a new "Schedule & assign" tab (bin picker + date + optional assignee, showing what's already scheduled for that date) are live now. Verified end to end: scheduled two bins for tomorrow, a repeat schedule call against the same date correctly skipped both as already-scheduled, listing by an arbitrary date via the new `GET /cycle-counts?date=` worked, and assigning one to a picker/packer correctly updated `assigned_to_name`.
- **Cold-chain temperature logging is genuinely new — no table for it existed anywhere before this build.** Section 9 asks for a log with gap/out-of-range alerting; the closest existing infrastructure (`is_cold_chain` on products, `zone = 'CC'` on bins) only ever marked *what* needs cold-chain handling, never logged the actual temperature of anything. A new `cold_chain_temperature_logs` table (one shop-wide reading stream, `in_range` computed and frozen at write time against the settings in force then — a later change to the configured range shouldn't silently reclassify history) plus `POST/GET /cold-chain/temperature-logs` and a `GET /cold-chain/gap-check` the web polls on page load, same "no background worker, compute live on request" pattern as M5's daily-request-review check.
- **No per-fridge/unit model exists anywhere in this build's schema** — a bin only ever carries a `zone` flag, never a specific piece of refrigeration equipment, and nothing in Section 9 or 10.2 describes one either. This build logs one shop-wide cold-chain reading stream rather than inventing a multi-unit concept the schema has never supported. 🔧 **Flagged, not guessed past**: if the shop actually runs more than one cold-chain unit (a separate vaccine fridge and a general cold-storage unit, say), each one needs its own gap/range tracking — worth a real answer from the Owner before this is relied on operationally.
- 🔧 **The acceptable range (2–8°C) and the max-gap-between-readings (8h) are seeded defaults, not owner-confirmed numbers** — 2–8°C is the standard WHO/vaccine cold-chain range, a defensible starting point rather than a fabricated one, and 8h assumes roughly twice-daily checks. Both are settings-table values (`cold_chain_temp_min_celsius`/`max_celsius`/`cold_chain_max_gap_hours`), editable the same way every other seeded threshold in this build is, once M13.9's settings screen exists.
- Verified live: an in-range reading (5.2°C) and an out-of-range one (11.5°C) both logged correctly with `in_range` computed at write time; `gap-check` correctly reported "no reading ever logged" before the first one existed, then correctly flipped to reporting the last reading as out-of-range once the second one landed; the Cold Chain screen's banner matched both states exactly.

## M13.9 — Section 10.2/15: Settings screen

- **No migration needed at all.** The `settings` table has carried `updated_at`/`updated_by` columns since M1, never once written to — every threshold this build has seeded since (55 rows by now, across nearly every milestone) already lives in one place, per Section 15's own instruction ("every configurable number goes in settings, not hardcoded"). This milestone is read/write parity for a table that was designed for it from the start, not a new mechanism: `GET /settings` lists everything, `PATCH /settings/:key` writes a new value, both Owner-only (these carry real business/compliance weight — GST state code, approval thresholds, escalation values — same bar as the Staff and Margins screens).
- **A settings edit takes effect immediately, not after the existing 30-second cache window.** `getSetting`'s in-process cache (added in M1, "revisit caching then if it needs to be instant" per its own comment) is invalidated for that one key the moment `updateSetting` writes it — verified live by changing `cold_chain_max_gap_hours` via the new endpoint and confirming `GET /cold-chain/gap-check` (a `getSetting` consumer) reflected the new value on the very next request, not up to 30 seconds later.
- **A value's new type must match its current one** — a number stays a number, a string stays a string, `null` can become anything (for the still-unset WhatsApp template names) and anything can be cleared back to `null`. This table backs real `getSetting<T>(key, fallback)` calls all over the app; a type-changing edit here wouldn't fail at the point of the mistake, it would surface later as a confusing runtime bug wherever that key is actually read. Verified live: writing a string into a number setting correctly 409s with `type_mismatch`, an unknown key correctly 409s with `not_found`.
- **Grouping on the settings screen ("Sales & billing," "Cycle counts & cold chain," etc.) is a client-side prefix match against each key, not a stored category** — there's no category column on `settings` and adding one just for display grouping isn't worth a schema change; the grouping is easy to get wrong or extend badly, and both are cheap to fix without touching data.
- **A real inconsistency caught by looking at everything in one place for the first time**: `order_batch_max_orders`/`delivery_batch_cap` (both 3), `order_batch_window_minutes`/`delivery_batch_window_minutes` (both 8), and `pending_order_response_target_minutes`/`order_response_target_minutes` (both 15) each look like the same threshold seeded twice under two different names — an early generic placeholder from M1's seed-settings migration, then a second, Section-7-specific set seeded again by M10's own delivery-orders migration once the real feature existed, with the first set never removed. Not touched here — collapsing either pair without checking which one each consuming code path actually reads could silently change behavior, and this milestone is about exposing what already exists, not refactoring it. Flagged for a real cleanup pass once it's confirmed which name (if not both) is actually load-bearing.

## M13.10 — Section 10.2: Reporting/query layer

- **The SQL console is read-only in two independent layers, deliberately redundant rather than trusting either alone.** A text check rejects anything that isn't a single `SELECT`/`WITH` statement before it ever reaches Postgres (a clear error instead of a cryptic one from below); the query then actually runs inside `SET TRANSACTION READ ONLY`, which Postgres itself enforces at the engine level regardless of how a write is spelled or wrapped. Verified live: a plain `DELETE` is rejected by the text check before touching the database; a data-modifying CTE (`WITH deleted AS (DELETE FROM users ... RETURNING id) SELECT * FROM deleted`) — syntactically a `WITH ... SELECT`, so it passes the text check — is still rejected, this time by Postgres itself ("cannot execute SELECT in a read-only transaction"), with zero rows actually affected either way. Always rolled back, never committed; a 5-second `statement_timeout` (verified live against `SELECT pg_sleep(10)`) and a 500-row response cap round out the defenses. Owner-only — a distinct, higher bar than every other report in this build, since this is raw database access even though it's read-only.
- **The prebuilt dashboard and the daily auto-report share one summary function** (`computeDailySummary`) rather than two separate aggregation paths that could quietly drift apart — the dashboard calls it live for "today"; the daily report calls it once for the business date just ending and freezes the result into a new `daily_reports` table, same snapshot-at-the-meaningful-moment reasoning as cycle counts' `system_quantity_base_units` and `batch_corrections`' `old_value`, so a report about a closed day never silently reflects data written after the fact.
- **The daily auto-report is a second WhatsApp trigger type on M8's existing dispatcher infrastructure, not a second notification mechanism.** `notification_log.trigger_type` was always a plain `text` column with no CHECK constraint restricting its values — adding `'daily_report'` needed no migration, just widening the TypeScript union and adding a message builder, following the exact pattern every other trigger already uses (a dedicated payload type, a short plain-text summary, a `whatsapp_trigger_daily_report_enabled` toggle and a `whatsapp_template_daily_report` setting matching every other trigger's naming). Unlike every other trigger, though, this one is Owner-facing, not customer-facing — sent to every active user with `role = 'owner'`, `recipientCustomerId` left `null`.
- **No background job runner exists in this build, so the daily report is generated by a plain `setInterval` poller in the API process** (5-minute tick) — exactly M8's own precedent for the WhatsApp queue processor (`processPendingNotifications`), not a new scheduling mechanism. `daily_reports.business_date` is `UNIQUE`, so a second tick the same day, or a restart mid-day, can never double-generate or double-send; the "generate at all" master switch (`daily_report_enabled`) and the WhatsApp-send sub-switch (`whatsapp_trigger_daily_report_enabled`) are separate, since an Owner might want the in-app snapshot kept for the record without also getting pinged. Verified live end to end: set the configured time to one already past and waited for a real poller tick (not simulated) — it generated and froze a `daily_reports` row for today with the live dashboard numbers, sent the WhatsApp summary to the seed Owner account (logged by the dev sender, per M8's still-unconfigured-Meta-credentials caveat), and the Daily Reports screen showed the frozen row.
- **"Shop-local time" is computed explicitly against `Asia/Kolkata`** (`Intl.DateTimeFormat` with an explicit `timeZone`), not read off whatever timezone the server OS or container happens to be in — the same unstated "local means IST" assumption M5's browser-side daily-request-review alarm already relies on for the client's clock, made explicit and enforced here instead of left to deployment-host luck.
